Skill 竞赛比的不是技术，是业务能力

本文目录 三股力量，把这场热推到了今天 两道门：技术门很低，业务门很高 口径判据 边界判据 复核判据 迭代判据 认真对待反方：门槛低恰恰是产业条件 满足感是燃料，也是陷阱 燃料这一面是真的 陷阱这一面也真实 Skill 只是 Input 端的一部分 收个尾

先看三组数字。

2026 年 5 月，iCourt 第二届全国法律人 AI 应用大赛总决赛在北京开赛，410 支队伍、超过 1500 名法律人报名。决赛现场，15 家律所、10 家企业、10 家高校同台，直播间累计 50 万人观看。

2026 年 7 月，深圳市律师协会首届 AI Skills 创新应用大赛决赛，十支队伍，展示的作品覆盖民事案情分析、婚姻家事、非诉工作底稿、涉港跨境、民间借贷、伤情鉴定、涉港继承。

2026 年 10 月，广东省第二届律师 AI 技能大赛启动报名，上届有 130 支队伍同台竞技。这一届的要求写得很硬：作品必须是自主设计、研发的法律服务 AI 应用，不接受概念产品，不接受纯贴牌。

这个密度说明一件事：这不是极客的玩具赛。省级律协、全国级赛事、云厂商冠名主办、商业机构联合协办，一整套产业动员的机器已经开动了。

那么问题来了：赢的是技术更好的那批人吗？

我的判断是：不是。赢的是业务能力更强的那批人。

我写 Skill 有一段时间了。上一篇文章我写 Skill 是洗漱包、工作区是浴室，说的是这两样东西各自住在哪一层。那一篇回答的是“哪个更好用”。这一篇我想说的是另一件事：当一群律师开始比赛谁做的 Skill 更能打，比的其实是什么。

三股力量，把这场热推到了今天

我先说清楚，我不是说这轮热是虚火。它的推力有三股，缺一不可。

第一股是商业逻辑。这一股最不浪漫，也最实在。厂商要的是律师的业务知识。那东西没法从代码里长出来，只能从真做过事情的人脑子里掏出来。Skill 是极好的载体：自封装、可分享、热插拔，你打磨好了传上来，平台零成本获得一批高质量业务内容，用户还自带传播热情。

更直白的证据在赛事组织名单里。iCourt 那场总决赛，阿里云、百度网讯、火山引擎是共同主办方；深圳那场，腾讯云的广东省泛政总经理到场致辞。云厂商不是来观摩的，是来占位的。平台要的是生态，生态要的是你把业务经验交出来。

第二股是功能性优势。官方这套设计确实精巧。Skill 走的是渐进式披露：平时只占一行书签的位置——名字加一句话说明；真派上用场了才翻开正文；正文提到的附件，用到哪页查哪页；脚本跑起来，只有输出进上下文，脚本代码本身不占地方。三个层级依次展开，装几十个技能对上下文的影响也很有限。

第三股是人的心理满足感。这一股最被低估，我自己也最有共鸣。

为什么偏偏是律师？

因为 Skill 是个轻技术重业务的扩展形态。做出一个能跑、结构符合规范的 Skill，技术上就是写几段提示词、调一次格式，一个晚上够用。难的是后面那段：让它在生产环境里稳跑。而后面那段需要的全是业务。

换个说法：Skill 的技术门槛低到足以让任何一个专业人士产生“我也能做”的判断，同时它又不要求你先懂技术。这个组合，对律师这种专业能力极强、技术背景为零的群体，是精准命中的。

那种感觉我说得再直白一点。第一次让 AI 按你自己写的规则跑完一份合同审查，看着它把你提醒过的那条风险点标出来，那种“我把它驯服了”的快感非常真实。这不是幻觉，是真实反馈，它值得被承认。

三股力量缺一不可。但只有第三股能解释为什么是律师。前两股对所有行业都通用。

两道门：技术门很低，业务门很高

这是全文的核心。把“做一个 Skill”拆成两段，难度差着几个量级。

技术门很矮。从零做出一个能运行、结构符合规范的 Skill：写清楚它是干什么的、怎么干、输出什么格式、禁止做什么，调通一次，跑通一个场景。一个晚上。

业务门很高。让它真正融入生产环境，在某个领域实现全自动或半自动的、高稳定性的高质量产出，这需要什么？需要制作者的业务能力，不是技术能力。

我把业务门拆成四条可证伪的判据。这不是唯一标准，是我自己在用的。

口径判据

你能不能说清楚“合格”是什么。同样一份合同审查任务，交付标准是“指出所有风险点”，还是“指出客户会付钱的那些风险点”，还是“指出这个客户历史上栽过跟头的那类风险点”？三个口径，三个完全不同的产出。口径定不下来，模型再强也只能给你一个平均分。口径从哪里来？从业务里来。

边界判据

材料不全怎么办？事实陈述自相矛盾怎么办？检索到的法条版本冲突怎么办？外部系统取不到数据怎么办？每一次“该不该停下来问人”的判断，都是业务决策，不是技术决策。一个不知道自己业务边界在哪儿的 Skill，会在任何一次意外输入面前露出原形。

复核判据

什么必须由人过一道，过的那一道具体看什么。这一条最接近律师的真实工作现场——你要能对人说清楚“这一版我已经人工核过了法条时效和事实引用”。深圳那场大赛的官方表述里有一句话，我觉得整篇报道最值得抄的就是这句：本次大赛“更加关注 AI Skills 能否嵌入律师真实工作流程”，参赛团队“重点展示事实材料边界、法律依据引用、人工复核节点及数据安全措施”。赛事方已经把评判落在业务层了。

迭代判据

法条改了，监管口径变了，客户偏好变了，你这个 Skill 怎么跟着变。这一条是持续性成本，也是最容易被低估的成本——大部分人算 Skill 的账，只算了第一次写的时间，没算往后每一次维护。

看看这些判据的共同点：没有一条是关于代码的。

而最有说服力的外部佐证，来自赛制本身。深圳大赛明确“摒弃同质化、概念化的创新展示模式”；广东省赛事的作品要求写明“须为自主设计、研发”，不接受概念产品和纯贴牌。赛制的门槛设在业务层，不在技术层。这是行业自己投的票，比我讲什么都管用。

还有一个细节更能说明问题。广东省这届要求每支队伍提交不超过 8 分钟的演示视频。8 分钟里你没法证明一个 Skill 稳不稳，你只能挑一个跑通的场景，把一次成功的输出演给大家看。所以这类比赛天然评的是“能不能演示”，不是“能不能生产”。它对业务能力的考察，只能靠评委在问答环节追问——你答不上来的那个问题，就是你业务能力的缺口。

同一份通知里还有一条：获认可的产品将集中上架“律满意”平台。官方给的是通往生产的路，不是通往领奖台的路。

技术上一个 Skill 只要一个晚上。业务上一个 Skill 要三年。

认真对待反方：门槛低恰恰是产业条件

这一节我不想跳过，因为对己方观点不利的证据，绕开反而更可疑。

反方会说：一个晚上就能做出来的东西，凭什么说它重要？

答：门槛低的东西不会被用于生产。演示阶段的技术门槛确实低，但从演示走到生产的那段距离，几乎全是业务。我前面列的四条判据，没有一条在演示环节会被问到——因为演示只需要挑一个跑通的场景，展示一次成功的输出就够了。

反方会说：有平台、有资源、有团队，还需要谈业务能力吗？

答：iCourt 那场决赛的参赛结构本身就有说服力。15 家律所、10 家企业、10 家高校同台竞技。高校和百人规模律所打的是同一场比赛，比的是同一批产物。技术投入差距最大的这两类人能被放在一张评审表上，说明赛场上比的确实不是算力、不是工程团队规模、不是烧了多少钱。

反方会说：你这是在贬低技术。

答：恰恰相反。是技术门槛太低，才让业务能力成为唯一的区分度。一件事的技术门槛一旦趋近于零，它就退化成一种背景噪音——所有人都会，那它就不再是区分点。真正稀缺的，永远是剩下那部分。

我甚至认为，低技术门槛不是这个赛制的缺陷，它是这个赛制得以存在的前提。如果做一个 Skill 需要一支工程团队三个月，这场比赛根本不会开办，只有一小撮技术合伙人能玩，行业普及也无从谈起。

所以低门槛不是问题。问题在于，多数参赛者把入场券当成了奖杯。

满足感是燃料，也是陷阱

把满足感只当燃料或者只当陷阱，都不诚实。它两面都是。

燃料这一面是真的

没有这层满足感，这一轮普及根本不会发生。设想一下，如果 Skill 是一个要先学 Python 才能上手的东西，律师群体的参与度会低得多。让一个专业人士在几十分钟内获得可感知的成果，这是普及的启动条件，不是虚荣。承认这一点比嘲笑它更诚实，也更有用。

陷阱这一面也真实

满足感有一个隐藏机制：它会在产出质量还很粗糙的时候提前兑现。

想一下反馈的时间点。比赛有奖状、有路演名次、有“我做的 Skill 拿了优胜奖”这种可以发朋友圈的东西。这些反馈来得又快又亮，把真正该问的问题压到了后面：这个 Skill 在生产环境里稳不稳？它出错的时候谁兜底？换一批材料、换一个案子，还成不成立？这些问题太慢、太不体面，而且没法在领奖台上回答。

所以我给一个具体的建议：把参加比赛当成一次业务体检，而不是一次成果展示。不是去证明我做了什么，而是借评委和同行的眼睛，找出我这套东西在真实业务里的边界在哪儿。评委问的每一个让你答不上来的问题，都是你业务能力的缺口，记下来，回去补。这场比赛能给你的最大收益不是名次，是那份问题清单。

坦白讲，这个道理我也花了些时间才想明白。我自己一度把“攒 Skill 的数量”当成了一种成就——那 106 个 Skill 的数字确实好看。但真正每天在生产环境里跑着的、出了错有人负责的、并且随着业务一起长进的东西，是另外几份，不在那个数字里。

Skill 只是 Input 端的一部分

这一节我想把话说准，因为标题里那个“技术”如果讲歪了，整篇就站不住。

Skill 干的事，本质是往模型的 Input 端输送更好的指令。官方把这件事拆成三层：

  • 元数据（每个技能的名字和一句话说明）常驻在系统提示词里，每个大约 100 个 token，用来决定“什么请求该唤醒它”
  • SKILL.md 正文在技能被触发时才读进上下文
  • 脚本和附件按需加载，脚本经执行后只有输出进入上下文，代码本身不进

看清楚这个结构：Skill 从头到尾作用在输入端。它不改变模型的推理能力，不改变工具本身的边界，不改变你能调用的数据范围，也不改变输出之后谁来判断对错。

所以结论很直白：把 Skill 做到极致，等于把提示词工程做到极致。这很有价值，但它是一个方向，不是一整张地图。

反过来说，这句话的正面版本更重要。会做 Skill 的人，天然比不会做的人多一块能力，多出来的这块还相当扎实——只是这块能力有明确的边界，越过这条边界的部分，Skill 一点忙都帮不上。

给读者三个可以立刻自查的问题：

  1. 除了写 Skill，你还懂不懂怎么跟模型对话、怎么判断它什么时候在编？
  2. 除了 Skill，你的工具链里有没有真正接通业务数据、结果能回流复盘的部分？
  3. 我做的这套东西，在我不开 Skill 的普通一天里，还剩多少用得上？

第三个问题最扎人，也最诚实。

Skill 是一块砖，不是一栋房子。会砌砖的人不自动会盖房子。

收个尾

那三场赛事的参赛人数还会涨，Skill 还会更多，热度也还会更高一阵。

但热潮退完之后留在桌面上的，是那几份真正在生产环境里跑着、出了错有人负责、并且随着业务一起长进的东西。这几份东西的作者，赢的不是因为代码写得好。

如果你也在做 Skill，下一个小时，别去调提示词的措辞。去你业务里找那件最烦的事——反复出错、每次都要重做一遍、至今没人写进规则的环节。规则一旦写出来，Skill 只是自动替你跑它的载体。

这段话我在四明山法师 AI 夜校上讲过几回。我的建议一直是先写一条，明天就用。别想着把二十年的手感一次写完，手感这种东西本来就只能一边用一边补。
