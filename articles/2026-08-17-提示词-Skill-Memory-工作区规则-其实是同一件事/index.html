提示词、Skill、Memory、工作区规则——其实是同一件事

本文目录 马甲不一样，里子是同一个 一张对照表，看清五件马甲 为什么 Skill 最火：它解决的是“长”的问题 规则放哪里：两个判断就够 三个误区：装错地方、装太多、换平台就慌 这套地图的边界 最后：学机制，不学名词

这两年 AI 领域的名词更新得比法规还快。提示词工程刚学会，又来了 Memory；Memory 还没用顺，Skill 火了；Skill 刚入门，人家又在聊 subagent。

每出一个新名词就学一遍，你累不累？

我说一个可能会让你松一口气的判断：这些东西在功能上是高度重叠的，它们做的都是同一件事——上下文管理。

马甲不一样，里子是同一个

所有这些机制，本质都是同一个动作：有一个文档，在软件启动或者加载工作区的时候被读一遍。

就这一遍，产生了“他记得你、他认识你、他懂你”的效果。

提示词是你手动把这段文字贴进对话框；工作区规则是它进这个文件夹时自动读；Memory 是它把平时对话里的要点记成小抄，下次开工前自己翻看；Skill 是把这个文档打了个包，还能发给别人装。

一张对照表，看清五件马甲

为什么 Skill 最火：它解决的是“长”的问题

用一个例子就懂了。交流会上我们当场拆过一个“律师助手” Skill：入口文件加分支规则文档，加起来上万字。

如果用提示词干同样的事，这上万字要一次性全部贴进对话框。两个问题立刻出现：输入端费钱，上万字每次都从头读一遍；更糟的是噪音——这个助手民事刑事行政都管，你的问题明明只涉及民事，但刑事行政的规则它也全都读了一遍，读了就会干扰回答质量。

Skill 的工程价值就在这：把一个巨长的提示词，变成一个按需加载的结构。启动时只读每个 Skill 的名字和一句话描述；真被调用了，才读入口文件全文；涉及具体板块了，才去读对应的分支文档；用到计算了，才运行脚本。

你需要哪块规则，它就用哪块。用更少的噪音、更低的算力，实现相同甚至更好的目标。

规则放哪里：两个判断就够

我自己的实践可以直说：我平时很少写 Skill，规则都沉淀在工作区里，按路由分级放在不同文件夹，跟着工作区自动加载。功能和 Skill 是等价的。

那什么时候值得封成 Skill？两个判断。

第一，这条规则要不要离开你的电脑。要分享给别人、要传到平台上去的，封成 Skill，打个包就走；只给自己用的，放工作区规则里就好，改动还更方便。

第二，这条规则跟着项目走还是跟着你走。只服务于某个工作场景的，放那个项目的工作区；你的身份、风格、通用偏好——比如输出要有易读性，先让人看着舒服——放用户级，让它跟着你走。

交流会上有同行问：能不能让 AI 自动总结我的使用习惯，自动生成 Skill？好消息是这个已经不难实现；但更基础的一步是先去问它一句：你的记忆里已经记了我什么东西？让它全部输出给你看。你会惊讶于它偷偷记了多少。

三个误区：装错地方、装太多、换平台就慌

什么都往 Skill 里装。不是所有规则都适合封装，跟着项目走的流程放工作区更顺手。

装太多。装 100 个 Skill，启动时它会把 100 个名字和描述全读一遍。描述写得马虎的 Skill 多了，互相干扰，该调起来的调不起来。数量少一点、质量精一点，比装一大堆管用。

以为换个平台就要重学。机制是通用的，名词是各家自己起的。这个平台叫记忆，那个平台叫风格文件，还有一个叫人格三件套——都是一个文档在启动时被读一遍。看懂里子，换马甲不用慌。

这套地图的边界

功能重叠不代表完全相同。subagent 的独立上下文隔离就是独一份的能力，主对话的噪音进不去，适合跑长链条的检索和批量处理。各家平台的具体实现细节也有差异，用之前看一眼文档里“什么时候被读”那一节，就够了。

最后：学机制，不学名词

名词每个季度都在换，机制不变。

下次再出一个新名词，先问两个问题：它的文档什么时候被读？它能不能离开我的电脑？答完这两个问题，你就已经懂它一大半了。
