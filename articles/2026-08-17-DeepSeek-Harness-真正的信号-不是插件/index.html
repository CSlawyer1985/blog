DeepSeek Harness 真正的信号，不是插件

本文目录 软件交付的东西，变了 改造者的身份，变了 这个理念，我手工实践了一年多 对法律人，这件事有具体的含义 泼点冷水 最后

8月13日，DeepSeek 发布了一个叫 Harness 的东西，MIT 协议开源。当天，GitHub 星数破了三万。

接下来几天，各种实测铺满了时间线：怎么安装、有哪些插件、四种模式怎么切换、界面长什么样。我看了几篇，都挺热闹，但都没说到点上。

我不是工程师，Harness 的技术内核我说不准。但它的架构口号只有一句话，这句话我熟——

Everything is a Plugin。一切皆插件。

模型、工具、技能、存储、界面，甚至 Agent 的工作循环本身，全部是可以拆、可以换、可以重组的插件。按官方的说法，这个系统里没有任何一块核心代码是不可以替换的。

这句话真正的分量，不在技术架构里，在它对"软件"这两个字的重新定义里。

软件交付的东西，变了

过去的软件，是开发者造好以后交给你用的。

功能是一份封闭的清单。你拿到手的那一刻，它就是它最终的样子。你能在清单里挑挑拣拣，但你改不了清单。想加功能？可以，提需求、等排期、等下个版本，主动权一直在开发者手里。

Harness 把这个关系反了过来。它交付的是一种可改造性：你拿到的不是成品，是一套随时可以拆开重组的系统。模型不顺手，换；工具缺一个，装；工作流不合理，重构。

说得调侃一点：它允许你随时把它推进手术室——缺什么器官就装什么器官，哪里不好用就现场整形。

所以评价标准也得跟着变。过去的软件，你问"它有什么功能"；现在你得问"它能被我变成什么"。前者买的是锤子，后者买的是铁匠铺。

改造者的身份，变了

更有意思的是第二个变化：谁在改造。

过去，改造软件是开发者的专利。用户能做的叫"反馈"——把诉求递上去，然后祈祷被听见。

插件化之后，改造权下放到用户手里。配置即改造，不需要读源码，不需要 fork 仓库。

而再往前走一步，就是这次真正让我觉得不一样的地方：主刀医生可以是 Agent 自己。

这不是修辞。一个 Agent 在干活时发现缺某个能力，它可以自己写一个插件，装上，接着干。你使用它的过程，本身也是它改造自己的过程。软件史上第一次，工具的使用者和工具的改造者是同一个主体——而且这个主体可以不是人。

Agent 不再只是改造工作对象，它开始改造承载自己的环境。

这个理念，我手工实践了一年多

说这话不是马后炮。

过去一年，我在 Claude Code 里手工搭建的，就是同一套东西。我的工作区分了几层：规则层，告诉 AI 什么该做、什么不该做；技能层，沉淀可复用的工作流；经验层，记录踩过的坑，跨会话生效；还有一层放我自己的方法论，告诉 AI 我是谁、我怎么想。

我还给它立了一条元规则：AI 产出不行的时候，先别急着换问法，多半是该改环境配置了。修 harness，优先于修 prompt。

举个真实的例子。AI 帮我做合同批注版文档，早期在文件格式上踩过坑，改出来的批注版排版是乱的。我没有每次都叮嘱一句"注意格式"，而是把坑记进经验库，把正确做法写进规则。从那以后，同类错误没再犯过。

这就是一次手工的插件手术：发现缺陷，定位到环境层，换掉那个模块，系统从此带着这个修复继续运行。

所以看到 Harness 发布，我的感受不是新奇，是确认。我在书和夜校里反复讲过一个类比：大模型是电力，人人都可以接；Harness 是配电系统，才是真正的壁垒。追模型的人接的是公共电网，建 Harness 的人拥有自己的配电系统。DeepSeek 这次做的，是把先行者手工验证过的路，浇成了公共基础设施。

对法律人，这件事有具体的含义

法律服务是个高度依赖个人经验的行业。一个律师值多少钱，很大程度取决于他脑子里有多少审查要点、多少踩过的坑。

问题是，这些资产过去的存在形态极差：锁在脑子里，散落在文档里。换一家律所、换一个工具，就清零一次。

插件化改变的是这一点：专业经验第一次有了可携带的技术形态。你的合同审查清单、你的知识库、你的写作风格，都可以做成模块，装进去，换下来，接着改。

我在《赋能法律人》里把 AI 使用能力分过三层：会用、会建、会改。大多数人停在第一层，而杠杆在后两层。Harness 这类架构的价值在于，它把"会改"的门槛从写代码拉到了改配置。第三层能力，第一次对非工程师开放。

往深了说，律所的竞争力也得换个算法：除了有多少人，还要看有多少经验被固化成了可复用的模块。

泼点冷水

先别急着把一切推上手术台。

第一个代价：不是每个人都想当外科医生。当一切都可以改，"不改"就显得像懒惰，"改什么"就成了新的焦虑。配置即自由，配置也即负担。我见过不少人折腾工具的时间远超用工具的时间，Harness 不会自动治好这个病。

第二个代价更隐蔽：永远在使用中重构的系统，可能永远躺在手术台上。我自己有过这样的阶段，改规则、调流程的时间，一度比用它们干活的时间还多。改造是有快感的，这种快感会吞噬使用本身。

我的应对纪律是给自己定一条优先级：能用规则解决的，不依赖记忆；能封装成工作流的，不依赖逐次提示。改造本身也需要方法，否则插件化只是新的混乱。

还有一些我判断不了的：插件生态会不会烂尾，热插拔的稳定性如何，v0.1 的接口还会变多少。这些都得走着看，我不装懂。

最后

Everything is a Plugin。

这句话真正的意思是：软件第一次承认，它交付时的样子，不该是它的最终样子。

过去我们评价一个工具，问的是"它现在能做什么"。今后更重要的问题是——

它还能被变成什么。以及，你想把它变成什么。

而这一次，回答这个问题的不只是你，还可以是它自己。
