一套规则喂饱三个 AI：法律工作区的多 agent 兼容改造

本文目录 先看透：各家 agent 用的其实是同一套规范 为什么推荐软链，而不是复制粘贴 操作：两行命令 一个必须避开的坑：别信它现编的入口名 效果与边界

一个越来越常见的尴尬：你在 A 工具里花了几个月，把一个法律工作区调教得服服帖帖——规则文件写得清楚，skill 各就各位，它知道你的文风、你的检索纪律、你的归档习惯。某天你想用 B 工具打开同一个工作区干点活，发现它两眼一抹黑：什么规则都不认识，从零开始。

几个月的调教，在第二个工具面前清零。多数人到这里就退回单工具了。其实破局只要两个字的操作：软链。

先看透：各家 agent 用的其实是同一套规范

在动手之前，值得先知道一个好消息：主流 agent 工具的扩展机制高度趋同。skill 的目录结构、命名规则、文件格式，各家基本一致（这套规范最早就是 Claude Code 定下来的，别家跟进了）；记忆文件都叫 memory；真正的差别只在入口文件的文件名。

Claude Code Codex 系 腾讯 CodeBuddy 系
规则入口文件 CLAUDE.md AGENTS.md CODEBUDDY.md
配置目录 .claude .codex .codebuddy
skill 存放 skills 目录，结构一致 同左 同左
记忆文件 memory memory memory

（各家产品迭代快，具体以你所用工具的官方文档为准。）

也就是说，你那套规则本身是通用的，B 工具不认，只是因为它找不到入口。它打开工作区时只会找自己认识的那个入口文件名——找不到，就当这个工作区没有规则。

为什么推荐软链，而不是复制粘贴

让 B 工具认到规则，笨办法是复制：把 CLAUDE.md 复制一份，改名成 B 认识的入口名。能用，但有个慢性病：从这一刻起你有两份规则。以后你在 A 工具里迭代了规则，B 那份不会跟着变，迟早出现两边规则不一样，而你忘了哪边是新的。

更好的办法是软链（symbolic link，符号链接）——让新文件名指向老文件，它不是一份拷贝，是同一份文件的另一个名字。改 CLAUDE.md，所有指向它的入口自动都是新的。永远不会失同步。

操作：两行命令

在你已经调教好的工作区目录下执行（macOS / Linux）：

ln -s CLAUDE.md AGENTS.md
ln -s CLAUDE.md CODEBUDDY.md

Windows 用户在管理员命令行里用 mklink AGENTS.md CLAUDE.md，效果相同。

就这么多。做完之后，支持 AGENTS.md 的工具、支持 CODEBUDDY.md 的工具，打开这个工作区，都会顺着入口读到你的整套规则。你也可以更懒：直接对新 agent 说一句“给 CLAUDE.md 做软链”，它会替你办了。

一个必须避开的坑：别信它现编的入口名

这件事里我上过一次当：让某个 agent 自己给自己写规则文件，它一本正经地创建了一个以自己产品名命名的入口文件。我后来专门去查了官方文档——根本没有这种入口文件类型，自然也不会被自动加载。模型很诚恳地编造了一份不存在的配置规范。

所以记住两条：入口文件名不要让它发挥，只认官方文档里列出的那几个；配完之后实测一遍，丢一条规则里的明确指令给它，看它执不执行——加载没加载，一试便知。

效果与边界

改完之后的效果是：同一套规则、同一批 skill，喂饱工作区里的每一个 agent。你在哪个工具里顺手就用哪个，规则资产只有一份，永远同步。

边界也要说清楚。软链打通的是“规则与 skill 的读取”，各家工具的能力差异还在：有的支持某类扩展，有的不支持；同一个 skill 在不同模型上的执行质量也有差别。我的用法是主力工具深度调教，其余工具借着这套规则做备用手——互为备份，还顺带互相检验规则写得清不清楚。

规则的本质是文本，入口的本质是路由。想通这一层，你就不会被任何一家工具的文件名锁住。
